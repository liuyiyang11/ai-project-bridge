# V0.2.1 Hardening

## Scope

V0.2.1 completes the hardening boundary for the existing asynchronous `code`-task runtime. It does not add a new task product or a new transport.

The migrated runtime is:

```text
MCP / Transport
      ↓
TaskSupervisor
      ↓
WorkerQueue
      ↓
TaskRunner
      ↓
TaskHandler
      ↓
Executor
      ↓
CodexSessionManager
```

GitHub and MCP code tasks both enter this runtime. GitHub keeps Issue parsing, trusted-actor validation, and status/comment/PR publication in its transport adapter; its code executor is invoked below `TaskRunner` and returns an explicit `TaskResult`. `experiment-review` and `presentation` remain compatible public interfaces, but are not migrated into this runtime. WPS, Dashboard, and Web API are excluded from V0.2.1.

## Startup contract

The MCP code-task entry is:

```text
bridge_start_code_task
      ↓
TaskSupervisor.start_code_task()
      ↓
WorkerQueue.submit()
```

`start_code_task()` validates the registered code project and request, creates a durable task in `QUEUED`, submits the TaskRunner job, and returns immediately:

```json
{
  "task_id": "task-...",
  "state": "QUEUED",
  "project": "registered-project"
}
```

MCP does not select this path through a public `start_task(task_type=...)` call and does not start Codex directly. A generic router can remain internally for compatibility.

## State, events, and results

TaskStore's durable snapshot is the business-state source of truth. Status readers use that snapshot, never WorkerQueue's Future state.

EventBus (`TaskEventBus` in the implementation) is the only runtime owner of business-state transitions. For each transition it validates the state-machine edge, appends the event, increments the task-local `event_seq`, and updates the snapshot state/cursor. TaskStore is responsible for durable file I/O, non-state metadata, and bounded artifact manifests; business code must not use `update_task(state=...)`.

Per-task snapshot writes share one durable lock, so a concurrent Codex metadata notification cannot roll a committed EventBus transition or its cursor back to an earlier snapshot. `TaskResult.metadata` cannot replace lifecycle, review-ready, stage, or event-cursor fields. After a task reaches review, control turns re-enter the same EventBus lifecycle before SessionManager sends the next turn.

TaskHandler returns one explicit `TaskResult`:

```text
{
  success: bool,
  review_ready: bool,
  message: str,
  artifacts: list,
  metadata: dict
}
```

TaskRunner uses this result rather than re-reading a snapshot to infer what the handler did:

```text
success=True  and review_ready=True  => RUNNING → WAITING_REVIEW
success=False                         => FAILED
```

The normal code-task lifecycle is `QUEUED → PREPARING → RUNNING → WAITING_REVIEW`. Exceptions during the lifecycle become `FAILED`. TaskRunner owns that lifecycle wrapper and exception capture; Executor owns worktree handling, Codex work, and file modification; CodexSessionManager owns session/thread/turn coordination.

## Worker and restart behavior

WorkerQueue is a scheduling component only. It owns Future submission, cancellation, and shutdown; it has no business-status model. A completed or failed Future does not itself make a task completed or failed.

`CodexSessionManager.wait_for_completion()` pumps deferred app-server notifications while waiting, so an asynchronous `turn/completed` notification is consumed even after the `turn/start` response has returned.

On restart:

- Persisted `QUEUED` code tasks are re-enqueued.
- Persisted `PREPARING` and `RUNNING` tasks are checked for safe recovery conditions, including a registered project, trusted worktree, and resumable persisted session.
- If safe resume cannot be established, the task becomes `UNKNOWN`, not `FAILED`.

## Documentation boundary

This document records the V0.2.1 runtime contract and scope. It does not report test or smoke-test results; those must be taken from an actual local or CI run.
